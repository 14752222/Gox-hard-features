# 统一验收口径

本集合里的任何一项，「做完」都不是「能跑起来」。下面的底线是**全部功能通用**的，
`features/*.md` 里再补各自的专属验收项。

## 一、可观测：必须证明「画出来了」

Gox 的失败模式有一个特点：**静默**。脚本不报错、测试全绿、窗口照开，
但某个组件就是空的（2026-10-15 实测：词云、热力图、KPI 大数字三处，
全部是靠人工看截图才发现的）。

所以每个功能至少要有一层**结构化断言**，而不是「跑一遍没崩」：

| 层级 | 手段 | 抓什么 |
|---|---|---|
| 节点层 | 遍历树断言关键节点布局盒非零 | 画布/组件没拿到尺寸（NaN 宽度这类） |
| 区域层 | 对面板内部矩形统计「颜色种类 + 非底色像素」 | 某一块整片空白 |
| 交互层 | 步骤表驱动（点击/输入/滚动）+ 每步断言 | 事件错位、状态没更新 |
| 语义层 | 属性快照（值/单位/取整后的最终值） | 换算与单位错乱 |

像素级比对**不作为判据**：三平台的系统字体不同，同一脚本本就不可能逐像素相等
（主仓 `gfx/gallery_shot_test.go` 文件头已写明这一点）。截图是给人看的，
断言是给 CI 看的，两者不是一回事。

## 二、可复现：确定性优先

- 数据一律用固定种子（参考 `gx-datav` 的 `makeRng` / `seriesRandomWalk`），
  不依赖 `Math.random()` 与真实时间；
- 涉及时间的功能（倒计时、时钟、动画）必须能注入时钟；
- 涉及定时器的测试走「一轮一个事件」的纪律（假 Surface 的唤醒通道一轮只消费一个信号，
  一次塞两个会让步骤与轮次错位）。

## 三、三平台：至少跑通矩阵

每个功能都要说明在 **win32 / x11 / cocoa**（涉移动端再加 android / ios / harmony）
上的差异与降级策略。平台差异是预期的，但不能是「没跑过所以不知道」。

## 四、不退化：性能与旧行为

- 帧预算不退化（主仓 `gfx/frame_budget_test.go` 是现成闸门）；
- 现有全量测试必须绿；**如果一项功能需要改旧测试的预期，说明它动了语义，
  必须在 RFC 里写明「哪些既有行为会变」并单独评审**。

## 五、可诊断：失败要指名道姓

断言失败信息里要能直接定位：脚本名 + 节点/区域 + 实测值。
反例：`画面近乎空白`。正例：`datav-widgets.js: canvas 布局盒为 {12 76 -9223372036854775808 44}`
（这条实测信息直接指向「宽度 prop 参与算术得到了 NaN」）。

## 六、留文档

落地时在 `features/*.md` 末尾补「落地记录」：实现提交、新增测试、
已知边界（哪些情况仍然不做，为什么）。
