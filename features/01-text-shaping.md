# 01 — 文本整形与字形回退

- 分层：文本 ｜ 难度 ★★★★★ ｜ 工作量 8–12 人周 ｜ 依赖：10、13

## 现状取证（主仓）

- `gfx/font.go` 文件头：系统字体经 `x/image/font/opentype` 解析，按字号懒建 face，
  `rune → glyph` 掩码做 LRU 缓存（键 = 字号|rune），并明写
  **「不做复杂 shaping：中西文按码位直排（任务书 P3 约定；连字/复杂脚本不支持）」**。
- `gfx/gallery_shot_test.go` 的 `galleryFontProbe` 注释：**「Gox 单字体、无逐字形回退」**——
  选中的基础字体没有 CJK 字形时，整屏中文静默消失（Linux CI 上真发生过）。
- 组件层已经到处在绕：`gx-datav` 里用 CJK 全宽 1.0em / ASCII 0.58em 的估算宽度
  （`theme.js` 的 `textWidth`）自己做排版。

## 为什么难

1. **shaping 不是「查表」**：要把 GSUB/GPOS 表按脚本规则跑一遍（阿拉伯上下文连写、
   印度系 reph/matra 重排、拉丁连字），再叠双向算法（UAX#9）与断行（UAX#14）。
   纯 Go 里做 HarfBuzz 等价物，等于把字体工程的半壁江山重写一遍。
2. **与「零外部运行时依赖」的定位冲突**：要么自研，要么引入 shaping 依赖
   （`go-text/typesetting` 一类）——引入就要过「单二进制 + 依赖审计」这道拍板。
3. **逐字形回退与 shaping 互相打架**：一个 run 里缺字要按码位切段换字体，
   但**切得太碎会打断连写**（阿拉伯一句话切成十段就废了）。回退粒度必须按
   script/cluster 而不是按字符。
4. **缓存键要重做**：现在是 `(字号|rune) → 掩码`，有了 shaping 之后键必须变成
   `(字号|字体|run 文本段)`，命中率模型、内存上限、失效策略全部要重新设计——
   而它处在**每一帧每条文字**的热路径上。
5. **表情**：彩色位图（COLRv1 / CBDT / sbix）、变体选择符、ZWJ 序列、国旗，
   与现有「字形掩码 → alpha 混合」的绘制模型不是一回事。

## 技术路线

1. **先解最疼的那一个**：字形覆盖探测 + 回退链（解决「中文整体消失」），
   与 shaping 解耦，可独立落地。
2. **run 切分与缓存改造**：按 script 边界切 run，缓存键升维，加命中率指标。
3. **shaping 子集**：先拉丁连字 + CJK 标点挤压（开合），不动复杂脚本。
4. **复杂脚本**：阿拉伯/天城文 + 双向算法（借道 07 的 RTL 布局镜像）。
5. **表情**：先单色字形，再彩色位图。

## 验收标准

- 多语言样本页（中 / 日 / 阿 / 天城文 / emoji / 混排）在三平台截图 + 结构化断言
  （每个样本区墨量 > 阈值，不是「跑通」）；
- 缺字回退：主字体缺字时自动落到回退链，不出现空白/豆腐块；
- 光标命中测试：坐标 ↔ 偏移在 cluster 边界上对齐（阿语光标不落在连写中间）；
- 缓存命中率指标可观测，帧预算不退化（`frame_budget_test.go`）。

## 主要风险

| 风险 | 缓解 |
|---|---|
| 引入 shaping 依赖破坏「零外部依赖」 | 先在 RFC 里拍板；备选是自研子集（工作量大但可控） |
| 缓存改造触及全部文字绘制路径 | 分阶段落地，每阶段都有三平台截图基线 |
| 表情彩色位图与现有绘制模型不匹配 | 先做单色 + 占位，彩色另立子任务 |
