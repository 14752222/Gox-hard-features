# 14 — 插件沙箱与能力隔离

- 分层：生态 ｜ 难度 ★★★★ ｜ 工作量 8–12 人周 ｜ 依赖：12

## 现状取证（主仓）

- `permissions/` 模块 + `docs/permissions.md` 已有权限体系（应用级声明）。
- `gx/*` 宿主模块提供文件、HTTP、剪贴板、存储、原生能力等宿主能力。
- 但**没有第三方代码的隔离**：任何脚本一旦加载，就与主脚本共享同一个
  全局对象、同一条 VM 线程、同一套宿主能力。

## 为什么难

1. **能力式授权**：现有权限是**应用级声明**，插件需要**运行期授予/降权**
   （插件 A 可读文件、插件 B 不可），还要能被用户撤销——权限模型要从
   「静态声明」升级为「运行时能力句柄」。
2. **全局隔离**：插件不能污染全局对象（原型链改写、内置对象打补丁），
   需要模块级 realm 或至少受控的全局视图；而与现有模块系统
   （`import` / 指令 / 全局注册表）的耦合点很多。
3. **资源配额**：VM 是**单线程确定性执行**的（README 设计取向），
   如何在字节码层插桩计步（CPU 配额）、统计内存与句柄，
   并且**不破坏确定性与性能**，是核心难题。
4. **崩溃隔离**：插件死循环或 panic 不能拖垮宿主。
   进程级隔离最稳，但与「单线程 + 单二进制 + 零依赖」的定位冲突；
   线程级隔离又拿不回确定性。
5. **签名与分发**：插件包签名、来源校验、版本与更新（与打包器联动）。
6. **调试体验**：隔离之后插件怎么调试（日志、断点、错误栈映射）。

## 技术路线

1. 权限声明 → 运行时能力句柄（可授予 / 可撤销）；
2. 模块级隔离（受控全局视图 + 内置对象只读视图）；
3. 配额插桩（字节码计步 / 内存与句柄统计）；
4. 崩溃隔离（先做「可中断的死循环」+ panic 捕获与降级，进程级隔离另立 RFC）；
5. 签名分发与版本；
6. 调试桥（日志通道 + 错误栈映射）。

## 验收标准

- 越权调用被拦且有明确错误（不静默失败）；
- 死循环插件可在预算内被打断，宿主不受影响；
- 插件 panic 不拖垮宿主（降级 + 可观测日志）；
- 配额超限可被观测（计数可查询）；
- 主脚本与插件互不污染全局（有断言）。

## 主要风险

| 风险 | 缓解 |
|---|---|
| 隔离与「单线程确定性」冲突 | 先做配额与崩溃捕获，进程级隔离作为备选方案单独立项 |
| 插桩影响性能 | 配额计数可开关，默认只在插件域开启 |
| 权限模型升级波及现有应用 | 现有应用按「全权」兼容映射 |
