# 10 — 高 DPI 与每显示器分数缩放

- 分层：渲染 ｜ 难度 ★★★★ ｜ 工作量 5–8 人周 ｜ 依赖：13

## 现状取证（主仓）

- `gfx/density.go` 已有 `displayScale` / `dpToPx`，`Scale == 1`（桌面 x11/win32）时
  换算恒等，移动端 >1。
- 同一文件的注释已经点明痛点：**「密度会变：窗口被拖到另一块屏、
  用户在系统里改缩放、折叠屏切换主副屏」**。
- 组件库里存在写死的像素常量（例如 `gx-datav` 的字号与行高直接给数字），
  dp/px 混用的历史债务需要一轮清理。

## 为什么难

1. **分数缩放（1.25 / 1.5 / 1.75）**：逻辑值 × 分数 → 设备像素必然出现小数，
   取整策略（四舍五入 / 向下 / 累积误差补偿）一改，**全局视觉回归全部要重拍**，
   而且 1px 边框在 1.5 倍下可能变 1.5px 灰边或消失。
2. **运行时 scale 突变**：拖到另一块屏时，字形掩码缓存、位图缓存、
   布局结果全部失效要重建，且要在一帧内完成，否则出现「先模糊后清晰」或闪烁。
3. **单位纪律**：所有写死的像素常量都要过一遍 `dpToPx`，
   漏一个就是「在 2x 屏上这条线细得看不见」。
4. **命中测试与光标**：设备像素 ↔ 逻辑坐标的双向换算，
   误差会让点击偏移、光标对不齐（验收要能量化）。
5. **三平台语义不同**：win32 DWM 缩放、macOS `backingScaleFactor`、
   X11 XRandR、移动端 density，且每显示器可不同。

## 技术路线

1. 单位纪律清理（常量全部走 dpToPx，加静态检查脚本）；
2. 分数缩放的取整策略（统一到一处，写清规则）；
3. scale 变化事件 → 缓存失效与重建（一帧内完成）；
4. 三平台矩阵验证 + 每显示器差异；
5. 截图基线与容差策略（不同 scale 各自一套基线）。

## 验收标准

- 1.0 / 1.25 / 1.5 / 2.0 四档视觉基线齐全，且都能过结构化断言；
- 拖到不同缩放的副屏后：不残留、不闪烁、文字清晰；
- 命中测试偏差 < 1 逻辑像素（有断言）；
- 移动端 density 链路不退化（进移动端回归清单）。

## 主要风险

| 风险 | 缓解 |
|---|---|
| 取整策略改动引发成片视觉变化 | 策略集中在一处 + 一次性重拍基线 |
| 缓存重建导致掉帧 | 重建分帧策略 + 帧预算闸门 |
| 历史像素常量遗漏 | 静态检查脚本进 CI（grep 级即可） |
