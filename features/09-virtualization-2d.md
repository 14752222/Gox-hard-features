# 09 — 大规模数据虚拟化（二维 / 树 / 变高）

- 分层：更新模型 ｜ 难度 ★★★★ ｜ 工作量 6–10 人周 ｜ 依赖：08、13

## 现状取证（主仓）

- `gfx/vlist.go` 已做**线性列表窗口化**：`scroll + vlist` 让十万行在建树期就塌回
  可见区间（`node.go` 注释记录了「十万行 ~800ms → 首轮即窗口化」这次实测优化）。
- 但覆盖面是**一维 + 已知行高为主**：二维网格、树形、变高项都还没进虚拟化。

## 为什么难

1. **变高项**：行高未知 → 滚动条长度只能估算 → 拖拽时位置漂移；
   测量缓存要按 key 存，并在数据/宽度变化时失效，还要处理
   「未测量的项用估算值，进入视口后回填真值导致的抖动（滚动锚定）」。
2. **二维虚拟化**：表格/看板/时间轴需要**行 × 列双向窗口化**，
   两个方向各自的估算与锚定、冻结行/列、合并单元格——比一维复杂一个量级
   （这也是「表格」被单列为高难度的原因之一）。
3. **树形**：展开/收起会整段改变行数，缩进层级与 key 稳定性、
   「父项滚出视口但子项在视口内」的裁剪规则。
4. **与 diff / 焦点 / 无障碍交叉**：**不在树上的项拿不到焦点、进不了无障碍树**，
   而虚拟化的本质就是「大部分项不在树上」——这与 08、无障碍是硬冲突，
   必须设计「虚拟项的逻辑节点」或代理层。
5. **滚动锚定与惯性**：数据插入/删除时保持视觉位置不变，
   与滚动动画同时进行时的时序。

## 技术路线

1. 变高测量缓存 + 估算回填 + 滚动锚定；
2. 二维窗口化（行 × 列，含冻结行列）；
3. 树形（展开态、缩进、key 稳定）；
4. 焦点与无障碍补齐（虚拟项的可达性）；
5. 滚动条拖拽精度与惯性。

## 验收标准

- 百万单元格网格滚动帧率达标（进 CI 性能基线）；
- 变高列表：滚动条长度误差 < 阈值，拖拽不漂移；
- 树形展开/收起不丢滚动位置与选中态；
- 虚拟项可被 Tab 到达、可被无障碍树枚举。

## 主要风险

| 风险 | 缓解 |
|---|---|
| 变高估算抖动导致视觉跳变 | 锚定策略 + 阈值内不修正 |
| 与 diff 的 key 模型冲突 | 与 08 统一 key 语义后再动 |
| 无障碍在虚拟化下缺失 | 明确「逻辑节点代理」方案，不做就写进已知边界 |
