# 08 — 增量 diff 与状态保留

- 分层：更新模型 ｜ 难度 ★★★★★ ｜ 工作量 8–12 人周 ｜ 依赖：09、13

## 现状取证（主仓）

- `gfx/condrender_test.go` 两处断言原文：
  **「外层信号变化应重建子树（v1 不做 diff）」**、**「分支切换应重建子树（v1 不做 diff）」**。
- 指令（`each` / `show`）展开也是重建：`directive.go` 里元素副本由指令自己造。
- 好处是语义简单可预测（这是 v1 的刻意选择），代价是**结构一变，状态全丢**。

## 为什么难

1. **协调算法本身**：keyed diff 要做插入/移动/删除的最小操作集，
   还要处理「同一个 key 换组件类型」「key 缺失/重复」这些边界。
2. **状态保留的面比想象中宽**：不只是输入框的值，还包括
   焦点、滚动位置、选区、动画进行中的插值、IME 组合态、组件内部 signal、
   以及**第三方的临时 UI 态**（展开/收起）。漏一个就是「列表重排后输入框内容串位」。
3. **与现有机制的交互很凶**：
   - `each` 指令的**实参先于外层求值**（`node.go` 注释：vlist 的 effect 在
     scroll 节点还不存在时就跑了一轮）——diff 要在这个顺序下仍然正确；
   - vlist 窗口化（09）里的项是「按需物化」的，与 diff 的 key 映射要统一；
   - 响应式 prop 的两轮接线（静态值优先）依赖当前的建树顺序。
4. **回归风险最高的一项**：现有 400+ 测试与全部组件语义都建立在「重建」之上，
   一动就可能成片变红，而且**红的是预期变了还是实现错了，往往要逐个判断**。
5. **收益要证明**：细粒度 signal 已经覆盖了「属性级更新」，
   diff 真正解决的是「结构变化时的状态保留」，范围要收窄，否则工作量失控。

## 技术路线

1. **白名单式状态保留**（不动 diff）：先保焦点 + 滚动位置 + 输入值，
   按 key 恢复——工作量小、风险低，能解 80% 的痛点；
2. **keyed `each` 稳定复用**：同 key 的项复用节点实例，不做通用 diff；
3. **通用 diff（可选）**：只在「组件库明确需要」的场景启用（表格行、列表项）；
4. **动画连续性**：结构变化时保留进行中的动画插值（与动画功能交叉）。

## 验收标准

- 列表重排 / 过滤后：输入框内容不串位、焦点不丢、滚动位置保持；
- 现有全量测试绿；若需改预期，逐条在 RFC 里列出理由；
- 大列表（1 万项）更新耗时进性能基线；
- 有明确的「diff 启用范围」文档（哪些指令/场景走 diff，哪些仍然重建）。

## 主要风险

| 风险 | 缓解 |
|---|---|
| 改动引发大范围回归 | 分阶段：先白名单恢复，再 keyed 复用，通用 diff 最后且可选 |
| 状态保留清单漏项导致诡异 bug | 先列全「状态清单」并逐项写断言 |
| 与 vlist / 指令顺序耦合 | 与 09 同步设计 key 映射，不各自为政 |
