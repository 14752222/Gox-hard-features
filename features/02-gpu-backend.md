# 02 — GPU 加速渲染后端

- 分层：渲染 ｜ 难度 ★★★★★ ｜ 工作量 20+ 人周（数人月）｜ 依赖：03、13

## 现状取证（主仓）

- `gfx/raster.go` 文件头：**「软件光栅化（P2）：实心矩形、1px 边框、背景色」**——
  整条渲染链是纯 Go CPU 位图。
- `gfx/backend/` 下只有**平台窗口后端**（android / darwin / ios / linux / windows / other），
  负责开窗与上屏，不负责 GPU 加速。
- README 定位：**「零 cgo、零外部运行时依赖、单二进制」**。

## 为什么难

1. **与定位正面冲突**：零 cgo 下接 Vulkan / Metal / D3D，要么手写 syscall 绑定
   （工程量巨大），要么引入驱动库（破坏「零外部依赖 + 单二进制」）。
   **这条必须先在 RFC 里拍板，否则做到一半会卡死在选型上。**
2. **批处理器**：要把「脏矩形 + 绘制原语」编译成顶点/纹理批次，
   而现在的绘制是**就地写帧缓冲**（`canvasTarget` 直接落 `image.RGBA`），
   需要先插一层 display list / 命令录制。
3. **文字**：字形掩码缓存要搬到 GPU 纹理图集（atlas），带来图集布局、
   碎片、失效与重建（换 DPI、换字体就整张重建）。
4. **确定性**：离屏回归（画廊截图 / 视觉回归）依赖 CPU 路径的确定性，
   GPU 路径必须**可关闭**，且两条路径的产出要在容差内一致——否则 13 号功能白做。
5. **半透明 / 圆角 / 裁剪 / 特效**在 GPU 上的实现与 CPU 路径天然有差异，
   视觉一致性本身就是一项长期工作。
6. 三平台各自的 API 与能力探测、无 GPU 环境的降级（回软件光栅）。

## 技术路线

1. 抽 `Renderer` 接口：软件实现（现状）+ GPU 实现（新），所有绘制走接口；
2. 命令录制层：把当前就地绘制改成 display list；
3. 单平台 GPU 原型（建议先 Metal 或 Vulkan 之一），只跑通「铺色块 + 纹理」；
4. 字形图集与批处理器；
5. 降级开关（能力探测失败 → 软件光栅）与一致性校验工具；
6. 三平台铺开 + 性能闸门。

## 验收标准

- 同一脚本 CPU / GPU 两条路径产出像素差在阈值内（含文字与半透明）；
- 无 GPU 环境自动降级且不报错；
- 离屏截图路径（回归用）完全不受影响；
- 4K / 大屏场景下帧耗时有可量化改善，并进 CI 性能基线。

## 主要风险

| 风险 | 缓解 |
|---|---|
| 选型与定位冲突 | RFC 前置拍板；备选是「只做合成层加速」而非全 GPU 化 |
| 视觉不一致导致回归失效 | 双路径一致性校验工具 + 容差策略 |
| 工程量失控 | 严格按里程碑交付，每个里程碑都能独立开关 |
