# 13 — 视觉回归与交互测试体系

- 分层：质量 ｜ 难度 ★★★★ ｜ 工作量 4–8 人周 ｜ 依赖：—（本项是其它项的地基）

## 现状取证（主仓）

- `gfx/gallery_shot_test.go`：离屏渲染真实上屏帧 + **非空白判据**
  （颜色种类 ≥ 8、非底色像素 ≥ 400）。文件头写明：PNG 按 GOOS 分目录，
  **不能当 golden 做逐像素比对**（字体来自系统字体，三平台本就不同）。
- **实测教训（2026-10-15）**：这套判据抓不住「单块面板静默消失」——
  词云、热力图、KPI 大数字三处全空，整帧断言照样全绿，最后靠人工看截图才发现。
  定位手段是临时写探针 dump 布局盒（拿到 `canvas` 盒宽 = `-9223372036854775808`，
  即 `int(NaN)`），才定位到「百分比宽度参与算术」。

## 为什么难

1. **像素比对天然不可行**：三平台字体不同 → 必须设计**结构化判据**
   （节点盒、区域墨量、属性快照），而结构化判据的阈值又要跨平台稳定，
   本身是一门手艺。
2. **交互时间线的确定性**：假 Surface 的事件通道一轮只消费一个唤醒信号，
   「一次塞两个事件」会让步骤与轮次错位；定时器是**进程级单例**，
   多个脚本互相污染（现状靠 `GlobalScheduler().ClearAll()` 兜）。
   要写「点击 → 输入 → 滚动」的多步脚本，框架必须把这套纪律封装掉。
3. **覆盖矩阵**：组件 × 属性 × 平台 × 缩放档位，组合爆炸；
   现在只有「整屏合成图」，单个组件没有独立截图脚本，
   于是「这个组件能不能画出来」没有直接证据。
4. **诊断性**：断言失败要说清「哪个节点 / 哪块区域 / 实测值是多少」，
   否则又要回到人肉翻截图。
5. **成本**：CI 上跑三平台矩阵 + 字体差异 + 截图存储，带宽与时长都是钱。

## 技术路线

1. **结构化断言三件套**（已开工一项）：
   - 节点层：canvas/关键节点布局盒非零（已加进 `gallery_shot_test.go`，
     实测能抓住 `int(NaN)` 这类静默失效）；
   - 区域层：面板内部矩形统计「颜色种类 + 非底色像素」；
   - 语义层：属性最终值快照（单位换算后）。
2. **每组件独立截图脚本**（现在只有合成屏，缺单组件证据）；
3. **交互脚本框架**：步骤表 + 确定性时钟 + 事件纪律封装；
4. **基线管理与差异视图**（按 GOOS × 缩放分目录，差异生成对比图）；
5. **变异验证**：故意把组件画空 / 尺寸置零，验证断言真的会红。

## 验收标准

- 每个组件有独立截图 + 至少一条结构化断言；
- 变异验证：注入「画出空画布」「盒宽置 0」的变异，测试必须失败；
- 失败信息指名：脚本名 + 节点/区域 + 实测值；
- 多步交互脚本（点击/输入/滚动）可复现，无步骤错位。

## 主要风险

| 风险 | 缓解 |
|---|---|
| 阈值跨平台不稳定 | 阈值取「明显低于实测值」的量级，只抓「什么都没画」 |
| 单组件脚本数量膨胀 | 先覆盖有绘制逻辑的组件（canvas 类），静态组件延后 |
| CI 时长与存储 | 截图按平台分目录、按需生成（默认不写文件） |
