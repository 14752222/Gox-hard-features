# 12 — 设计令牌与运行时换肤

- 分层：生态 ｜ 难度 ★★★ ｜ 工作量 3–5 人周 ｜ 依赖：13

## 现状取证（主仓）

- `docs/theme.md` 存在，0.9.0 已落 **32 项颜色 token**。
- 但一批样式值在内核写死：`docs/v1-roadmap.md` P1-8 列了 9 项 ——
  焦点虚线框色 / 滚动条与滑块色 / select 箭头 / progress 轨道色 /
  checkbox 未选中底色 / modal 遮罩 / switch 滑块 / disabled 降饱和 /
  光标闪烁周期。原文结论：**「不收编成 token，主题切换会有视觉残留」**。
- 第三方组件库 `gx-datav` 自带 `palette`（`theme.js`），不跟随内核主题。

## 为什么难

1. **收编过程本身就是回归风险**：每收编一个写死值，都可能让某个组件在某个平台上
   「看起来变了」——而这正是「没有视觉回归（13）就做不动」的典型场景。
2. **继承与覆盖语义**：全局 / 子树 / 组件级三层覆盖，优先级怎么定？
   token 值本身是 signal 吗（要不要可订阅）？
3. **运行时切换的代价**：切换主题应只重绘受影响的节点，
   而现状是「属性值变化 → 标脏重绘」或「结构变化 → 重建」；
   主题跨越所有节点，容易退化成整树重建（与 08 交叉）。
4. **分层设计**：primitive（色板）→ semantic（语义：成功/警告/背景/边框）
   → component（组件专用）三层要不要全做？做浅了不够用，做深了组件要改一大片。
5. **第三方契约**：`gx-datav` 这类库自带常量，如何让它们跟随主题
   （要么读内核 token，要么接受外部注入）——这需要定一个**公开的取色契约**。

## 技术路线

1. 定义令牌分层（primitive / semantic / component）与命名规范；
2. 收编 9 项写死值（每项一个子任务，各自带截图基线）；
3. 继承与覆盖语义（子树级覆盖 + 订阅）；
4. 运行时切换：增量标脏而非重建；
5. 公开取色契约 + `gx-datav` 接入示范。

## 验收标准

- 明暗切换只重绘受影响节点（节点重绘计数断言，不是「看起来没问题」）；
- 全组件 × 双主题截图矩阵，无视觉残留（无写死色）；
- 第三方组件库跟随主题（有示范与契约文档）；
- 对比度达标（正文 ≥ 4.5:1，有计算脚本）。

## 主要风险

| 风险 | 缓解 |
|---|---|
| 收编引发视觉回归 | 依赖 13 的截图矩阵；一次只收一项 |
| 切换主题退化成整树重建 | 与 08 共用「标脏而非重建」的路径 |
| 分层设计过度 | 先做两层（primitive + semantic），component 层按需 |
