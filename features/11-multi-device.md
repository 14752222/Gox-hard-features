# 11 — 多屏协同与跨设备 UI

- 分层：平台 ｜ 难度 ★★★★★ ｜ 工作量 8–14 人周 ｜ 依赖：10、08

## 现状取证（主仓）

- `gfx/screen.go` 已有多屏与姿态能力：JS 侧 `screens()` / `primaryScreen()` /
  `screen(id)` / `screenOf` / `useScreen()` / `usePosture()` 等一整套订阅接口。
- `docs/multi-window.md`、`gfx/multiscreen_test.go` 说明多窗口已有基础。
- 但「多屏」目前停留在**查询与订阅**层：跨屏迁移的状态保持、跨设备协同、
  远程渲染都还没有。

## 为什么难

1. **跨屏迁移**：窗口从主屏拖到副屏时，DPI 可能变（10）、可用区变、
   布局要重排、字形/位图缓存要重建——**同时还要保持内部状态**（滚动位置、
   未保存的输入、进行中的动画），这直接依赖 08。
2. **折叠屏姿态**：展开/折叠改变的是「可用区形状」甚至「应用是否跨两个物理屏」，
   姿态事件要在单帧内落到布局，且不能丢状态；移动端回归清单里
   「分屏折叠」是明确的 v1 边界项。
3. **跨设备协同**（真正的多设备）：一个界面状态在多台设备间同步，
   涉及冲突解决、网络边界、离线、设备能力差异（屏幕尺寸/DPI/输入方式不同）。
4. **坐标系**：多显示器存在负坐标、原点不一致、任务栏避让区，
   命中测试与弹层定位都要按「屏幕局部坐标」而不是全局坐标算。
5. **远程渲染**（可选但很诱人）：把界面串流到另一台设备，
   需要把渲染与事件通道分离——而现在是「渲染与事件在同一线程、同一 Surface」的纪律
   （假 Surface / 事件纪律的前提）。

## 技术路线

1. 显示/姿态变化事件的收敛与单帧生效；
2. 跨屏迁移的状态保持（与 08 的保留清单共用）；
3. 多屏坐标系与弹层定位修正；
4. 折叠姿态的布局连续性（进移动端回归清单）；
5. 跨设备状态同步（可选，先做单主多从）；
6. 远程渲染（可选，先做投屏镜像）。

## 验收标准

- 拖到不同 DPI 的副屏：布局正确、文字清晰、状态不丢（含输入框内容与滚动位置）；
- 折叠/展开切换：布局在一帧内完成，不丢状态；
- 多屏负坐标下：弹层与菜单定位正确（有断言）；
- 姿态事件不重复触发、不丢事件（事件计数断言）。

## 主要风险

| 风险 | 缓解 |
|---|---|
| 与 DPI / diff 强耦合，容易做成一半 | 明确第 2 步依赖 08 的白名单状态保留先落地 |
| 折叠屏无真机 | 用桌面资产测试覆盖逻辑 + 模拟器/契约测试（主仓已有先例） |
| 跨设备同步范围失控 | 先只做「状态同步」，远程渲染另立 RFC |
