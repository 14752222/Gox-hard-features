# Gox 高难度功能集合

> 本仓不是 Gox 主仓的代码副本，而是**高难度功能的“管理仓”**：
> 把主仓里那些「牵一发动全身、必须单独设计评审、不可能顺手做掉」的能力
> 单独拎出来，做**现状取证 → 难点拆解 → 技术路线 → 验收标准 → 看板跟踪**。

- 主仓（引擎与组件库）：<https://github.com/14752222/Gox>
- 本仓（本集合的设计与跟踪）：<https://github.com/14752222/Gox-hard-features>

## 为什么单独开仓

Gox 的引擎仓以「一次提交 = 一条可回归的语义/能力」为节奏：改动必须自带测试、
必须能过三平台矩阵。但下面这类功能**不是**这个节奏能承载的：

1. **改动面横跨多个子系统**（例如文本整形要同时动字体、缓存、命中测试、绘制、截图基线）；
2. **需要先拍板架构选型**（例如 GPU 后端与「零 cgo / 单二进制」这条定位直接冲突）；
3. **工程量以人月计，中途要长期挂看板**（例如富文本编辑器）；
4. **失败是静默的**——跑得起来、测试全绿，但画面上缺一块（本轮实测：词云 / 热力图 /
   KPI 大数字三处静默失效都是靠目检才发现的）。

这类东西塞进主仓的 issue 列表会被日常提交冲掉，所以单独开仓，用 RFC + 里程碑 + issue
管理，主仓只承接「已定案、可拆、可回归」的子任务。

## 状态图例

| 状态 | 含义 |
|---|---|
| `草案` | 已完成现状取证与难点拆解，尚未评审 |
| `已评审` | 路线与验收已拍板，可以开始拆子任务 |
| `进行中` | 主仓已有对应子任务在跑 |
| `已落地` | 主仓已实现且有回归覆盖 |
| `搁置` | 与定位冲突或收益不足，暂不推进（需写清理由） |

## 工作流程

1. 从 `rfcs/0000-rfc-template.md` 复制一份 → 填「现状取证 / 方案对比 / 取舍 / 验收」；
2. 评审通过 → 状态改 `已评审`，在 GitHub 上建里程碑与子任务 issue（打 `area:*` / `difficulty:*` 标签）；
3. 子任务进主仓实施，**每个子任务必须自带回归**（口径见 `docs/acceptance.md`）；
4. 全部子任务合入 → 状态改 `已落地`，在 `features/*.md` 末尾补「落地记录」。

## 与主仓的边界

- 本仓**只放设计与验收**，不放引擎实现代码（实现一律进主仓，保证可回归）；
- 例外：一次性探针 / 变异验证脚本可以放 `probes/`，但它们不属于交付物；
- 主仓的 `docs/v1-roadmap.md` 管「v1 还差什么」（缺口），本仓管「什么东西难做」（能力），
  两者会互相引用但职责不重叠。
